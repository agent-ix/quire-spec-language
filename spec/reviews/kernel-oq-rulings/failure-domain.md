# SR-511: Kernel-convergence rulings OQ-A to OQ-F failure-domain review

## Summary

Looks for identity confusion, domain mixing and ordering edge cases in how
PR #351 records OQ-B to OQ-F, and whether the new TCs would catch the faults
they name. QSpec was read at `2449ceb`: FR-141 `:60-91`, FR-142 `:114-142`,
FR-144 `:106-136`, FR-204, FR-208 and `model-complete.md:226-251`.

The reference-key recording (universe, then type, then object; authored
object bytes) matches `model-complete.md` and the TC-198 L09 vectors. Two
ordering problems are serious. The enum rulings are recorded as covering every
"sum", including variants that carry payloads. TC-252 step 6 expects variant
identities to survive a reordering that FR-141 says changes them. Several
tests would also pass faulty implementations.

## Verdict

**REVISE.** FND-001 and FND-002 (high) make O-14 and TC-252 contradict QSpec
FR-141/FR-144 for inputs the spec admits. FND-003 to FND-008 (medium) are
rank/identity invariants the spec does not state, and tests that cannot fail
on the faults they claim to catch.

## Findings

| ID | Severity | Summary | Refs |
| --- | --- | --- | --- |
| FND-001 | high | OQ-D and OQ-F rule on **enum** values, but ADR-013 records them for every **sum**. The O-14 "Sum types" cell (`:360`) says a sum value "carries its `VariantId` and its rank" and that "the canonical key of a sum value is its rank". QC-15 (`:1026`) types `VariantId` as "(enum and sum)". FR-088 `:169-186` and C-26 (`:888`) do the same. ADR-012 sums have variants with payloads ("Variant payload types resolve through the type environment", ADR-012 `:147-148`). The FR-141 member preimage `{version, declaration_node_id, case}` covers only payload-free enum cases, and QSpec at `2449ceb` defines no sum type. A payload-carrying sum keyed by rank alone breaks FR-144's rule that "two values have equal keys exactly when they are FR-149 equal" (`FR-144:106-107`): two values of one variant with different payloads get equal keys. The PR also removes TC-252 step 3's payload-carrying variant ("one wrapping another composite type"), which hides the gap. **Fix:** scope the OQ-D/OQ-F text in O-14, T-6, QC-15, C-26 and FR-088 to enum (payload-free) variants. For a sum variant with a payload, say its identity and key are open until agent-ix/quire-specification#115 defines them, e.g. key = (rank, payload key). Restore TC-252's payload-variant case, marked planned against #115. | ADR-013:360, :848, :888, :1026, :1095, :1097; FR-088:169-186; TC-252 step 3; ADR-012:147-148; QSpec FR-144:106-107 |
| FND-002 | high | TC-252 step 6 and its expected result say that reordering the sum's declared variants leaves every `VariantId` unchanged, because "it is a digest over the declaring sum and the member, not an index". Under OQ-F, a `VariantId` is the FR-141 member key over `declaration_node_id`. For an **ordered** enum, the declaration preimage's `members` list is in declaration order, so a reorder produces a new declaration node key and therefore a new `VariantId` for every case (FR-141 `:64-66`, `:71-75`, `:84-86`: "insertion or reordering therefore creates a new declaration revision"). Only an unordered enum is invariant. The current test (`src/check/identity.rs:899-905`) reorders while holding `sum_node` fixed, which is not a reachable state under FR-141. **Fix:** split step 6. (a) Unordered enum: reordering the source cases changes neither the declaration key, nor any `VariantId`, nor any rank. (b) Ordered enum: reordering changes the declaration key, every `VariantId` and the ranks. Build the test from source, so the node key is recomputed rather than held fixed. | TC-252 step 6 and expected results; FR-088-AC-10; QSpec FR-141:64-86; src/check/identity.rs:899-905 |
| FND-003 | medium | The rank/`VariantId` invariant is not stated. The kernel carries a rank beside the `VariantId` and orders by rank alone. Equality uses the `VariantId` alone. The spec never says that the rank is a function of the `VariantId` within its shape, or who enforces that. A value with a well-formed `VariantId` and a wrong rank would be equal to the correct value and still get a different key, which breaks FR-144's "equal keys exactly when equal". Two values of different enums with equal rank would compare as equal keys in `compare_keys`: ADR-013 relies on the checker ("never share a collection", `:360`), but the kernel is a leaf and cannot see that. The kernel `EnumShape` (`quire-exact/src/value.rs:73`) is a `BTreeSet<VariantId>` and carries no ranks. **Fix:** in O-14/T-6, state that the kernel sum shape maps each `VariantId` to its rank, and that `ValueType::admits` refuses a value whose (`VariantId`, rank) pair is not in the shape. State that `compare_keys` refuses, with `CheckedInvariant` as for the population pair, when ranks are equal and `VariantId`s differ. Add both to TC-409. | ADR-013:360, :848; FR-088:176-186; quire-exact/src/value.rs:73, :154; QSpec FR-144:106-107 |
| FND-004 | medium | TC-409 says it "catches ... a rank that takes part in equality", but step 5 compares two copies of `E::a`. They share both `VariantId` and rank, so an implementation that includes rank in equality passes. **Fix:** add a step that builds two kernel values with an equal `VariantId` and different ranks, directly through the kernel constructor, and expects the FND-003 refusal. Or delete the fourth fault from the Description. | TC-409 Description, step 5 |
| FND-005 | medium | TC-410 would pass a faulty implementation that builds one universe per root type. Both of its components, `{A, B}` and `{X}`, have one root, so digests over `[A]` and `[X]` are also what a per-root implementation produces. OQ-E and `model-complete.md:228-231` define the universe over "the ascending array of effective type identities in that component that have no supertype". With multiple inheritance, one component can have several roots. **Fix:** add a third component to TC-410 and FR-084-AC-7: roots `C` and `D`, and `E` with `supertypes: [C, D]`. Expect an `E` member's universe to equal the digest over the model selection and `[C, D]` in ascending effective-identity order, the same universe for `C` and `D` members, and a universe different from `A`'s and `X`'s. | TC-410; FR-084-AC-7 (FR-084:192); QSpec model-complete.md:228-231 |
| FND-006 | medium | `VariantId` and the declared `UnitId` hold bytes in `quire.checked-semantic-node/v1`, the same domain as `NodeKey`. Under R-04 (`ADR-013:90`), a `VariantId` and its member's `NodeKey` with equal bytes are therefore the same identity in two types. The recording says the kernel shape "carries no `NodeKey`" (`:360`, FR-088 `:176-178`), which is true only at the type level. C-26 performs a `NodeKey` → `VariantId` byte transfer and the unit path a `NodeKey` → `UnitId` transfer, and neither is named as a conversion. O-05 rejects exactly this kind of transfer between `EffectiveId` and `NodeKey`. Nothing restricts which node keys reach those constructors: a dimension node key or an enum-declaration key (same domain) is accepted as a declared `UnitId` or `VariantId`, and the kernel cannot tell them apart because the preimage version (`quire.unit-node/v1`, `quire.enum-member-node/v1`) is not carried. **Fix:** list both transfers in §4 as conversions: C-26 for `VariantId`, and a new C row for the `Quantity` unit, with the preimage kind each accepts. Name their only callers under ADR-011 T-12, as for `NodeKey`/`EffectiveId`/`PopulationId` (ADR-011 `:747-750`). See SR-510 FND-002. | ADR-013:90, :360, :848, :888, :1093, :1097; FR-088:176-178; ADR-011:747-750 |
| FND-007 | medium | FR-088-AC-11 (`:212`), TC-409 step 6 and the OQ-D reason (`ADR-013:1095`) say that changing the package's declared version changes every `VariantId`, "because the sum's node key includes `name@version` (QC-18)". QC-18 is an unlanded request about QSL's generic node-identity preimage (`:1029`). FR-141's enum declaration preimage is `{version, owner, qualified_declaration, ordered, members}`, where `owner` is "the stable subject projection of an exact admitted source" (FR-141 `:70-75`). FR-141 `:86-88` says "The same exact imported owner and declaration retain the same keys across otherwise different packages". Whether a version bump changes the enum key depends on `owner`, not on QC-18. The AC may assert behaviour QSpec does not give. **Fix:** in AC-11 and TC-409 step 6, use an edit that FR-141 guarantees changes the member key without changing ranks. A change of `owner` or of the enum's qualified declaration name, keeping its cases and their order, does this. Drop the QC-18 clause from the OQ-D reason, or cite the FR-141 `owner` field instead. | FR-088:212; TC-409 step 6; ADR-013:1029, :1095; QSpec FR-141:70-88 |
| FND-008 | medium | TC-410 and FR-084 `:163-164` rely on one population admitting members from two universes: step 2 admits one closed population covering `B` and `X`. QSpec says "A population is a membership view inside a universe" (`model-complete.md:232`), and neither the rulings nor FR-084 decide whether a population may span universes. The code keeps one `universe` per binding (`src/model/population.rs:501`). FR-084-AC-5's foreign-universe refusal (`:129-130`, keyed on `T`'s universe) also changes meaning with a multi-universe binding. **Fix:** either rewrite TC-410 to use two populations, one per component, so it tests OQ-E without the open question, or add an FR-084 statement, with a QSpec citation, that a binding may span universes and each member carries its own. The second option needs a QSpec question if `model-complete.md` does not already allow it. | TC-410 step 2; FR-084:129-130, :163-164; QSpec model-complete.md:232; src/model/population.rs:501 |
| FND-009 | low | FR-084's universe section (`:153-167`) defines universes only for object types. QSpec FR-208 gives a process "an object universe of runs" (`model-complete.md:164`; FR-208 `:47`, `:81`), and a population member type may name a process (`model-complete.md:163`). The universe of a process-typed member, and the `ObjectId` of a run, are unspecified here. **Fix:** add one sentence that scopes FR-084's universe rule to object types and cites FR-208 for process run universes, or state the process case. | FR-084:153-167; QSpec FR-208:47, :81; model-complete.md:163-164 |
| FND-010 | low | `ObjectId` is now an unbounded authored UTF-8 string in the kernel, where it was a fixed 32 bytes. Reference-key comparison in `compare_keys` becomes linear in caller-supplied object length. The spec does not say whether that comparison is metered or whether the kernel bounds object length. **Fix:** in T-6/QC-15, state that the kernel either charges reference-key comparison by object byte length under `quire.value.accounting/v1`, or relies on an admission-time length bound (name it). | ADR-013:848, :1026 |
