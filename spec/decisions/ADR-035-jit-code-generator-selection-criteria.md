# ADR-035: JIT code generator: Cranelift behind the execution-backend seam, with the criteria that would reopen it

Status: Accepted. The owner decided RES-56: `qsl-jit` uses Cranelift for
now, behind the ExecutionBackend seam (FR-294). CG-4 (unsafe code in
`qsl-jit`) remains an open ruling.

## Context

ADR-029 EB-7 fixes the execution-backend seam (FR-294) and the JIT semantics
(EB-4, FR-295). As first written it left the code generator to a benchmark
(RES-56): Cranelift or LLVM. EB-4 binds either one. The owner has decided the choice for now:
Cranelift. This record states that decision, the criteria that support it,
and the conditions under which it is reopened.

The two candidates differ along lines that matter to QSL:

- **Build.** QSL's README promises that a clean clone builds with only a Rust
  toolchain (NFR-017). Cranelift is a set of crates.io crates. An LLVM
  binding needs an LLVM installation on the build host, or a bundled build of
  LLVM.
- **Translation time against code quality.** `prepare` is charged per
  translated node (FR-294 "Prepare charges"), and a JIT is only worth having
  if preparation plus execution beats the interpreter. Cranelift translates
  faster; LLVM usually produces faster code.
- **Boundaries.** Both must call only the kernel table (FR-561), report each
  generated block's byte length before it is kept (FR-294), and expose
  relocation records that FR-561-AC-3 inspects.

The coverage the JIT translates is FR-560, the fast-path rule is FR-562 and
the parity gate that holds the JIT to the interpreter is FR-563. None of them
depends on this decision.

## Decision

**`qsl-jit` generates code with Cranelift.** The JIT is reached only through
the ExecutionBackend seam (FR-294), so replacing the code generator later
changes `qsl-jit` alone: no caller, no outcome and no parity rule changes
(EB-4, FR-295). LLVM is not used, by default or behind a feature.

The criteria below are the rationale for that choice and the conditions that
reopen it.

### CG-1 Must criteria

A code generator that fails any of these cannot be the JIT's. Cranelift is
chosen as meeting them; the Phase 4a spike (CG-2) confirms each, and a
failure is CG-3 reopen condition 1:

1. **Rust-only default build.** The default workspace build and the
   NFR-017 clean-clone gate stay Rust-only: the code generator needs no
   system library.
2. **Prepare accounting.** The code generator lets `qsl-jit` charge
   `compile_work_units` before translating each checked node and
   `code_bytes` with each block's byte length before keeping it, and poll
   `&Cancel` at each charge (FR-294).
3. **Call boundary.** Generated code calls only `KernelTable` entries and
   blocks of the same prepared value, and the code generator exposes the
   relocation records that show it (FR-561).
4. **Determinism.** The same checked entries and `PrepareLimits` produce the
   same generated bytes before relocation, so a parity difference reproduces
   from its seed and index (FR-295, FR-563).
5. **Licence.** The code generator's licence is compatible with
   `AGPL-3.0-or-later`.
6. **Targets.** The code generator generates code for `x86_64-unknown-linux-gnu`
   and `aarch64-unknown-linux-gnu`.

### CG-2 The sanity spike (Phase 4a)

When `qsl-jit` is first built (Phase 4a), a sanity spike records these
numbers for the Cranelift JIT, and confirms each CG-1 criterion, over the FR-295 parity program generator's
10,000 units at the gate's default seed and their argument tuples, on each
CG-1 item 6 target, release profile. The spike records numbers; it does not
re-run the choice:

| Measure | Definition |
| --- | --- |
| Prepare time | Wall time of `prepare` over every function of each unit, summed over the units |
| Run time | Wall time of every argument tuple's `call`, summed |
| Interpreter time | The same calls on the interpreter backend, summed |
| Code bytes | The `code_bytes` counter `prepare` reaches, summed |
| Build cost | Clean-clone `cargo build --locked -p qsl-jit` wall time and the number of packages it adds to `Cargo.lock` |
| Unsafe sites | The number of `unsafe` blocks and `unsafe fn` in `qsl-jit` Cranelift requires |

The spike's JIT also passes the FR-563 parity gate.

### CG-3 Reopen conditions

This record is reopened only when the spike, or later use, shows a blocker:

1. Cranelift fails a CG-1 must criterion (for example, it cannot charge
   `PrepareLimits` per node, or cannot target one of the CG-1 item 6
   targets).
2. The Cranelift JIT cannot pass the FR-563 parity gate because of the code
   generator, not because of a `qsl-jit` defect.
3. Prepare time plus run time is not below the interpreter time on
   `x86_64-unknown-linux-gnu`, so the JIT gives no speed-up.

Slower numbers than hoped are not a blocker. Without a blocker, the spike's
numbers are recorded and the decision stands. If condition 3 holds, the
reopened decision includes not building the JIT: EB-8's `jit` choice then
keeps refusing as not supplied (FR-296).

### CG-4 Unsafe code in `qsl-jit` (open ruling)

Entering generated machine code requires `unsafe`. Every QSL crate today
declares `unsafe_code = "forbid"`. This record proposes that `qsl-jit` is the
one exception: `unsafe` confined to one module that maps generated code and
enters it, every other `qsl-jit` module and every other QSL crate keeping
`forbid`. This is an open ruling: it needs the owner's decision before
`qsl-jit` is built, and the ruling is recorded here when made.

## Consequences

- `qsl-jit` depends on Cranelift crates from crates.io, so the outside-user
  build stays Rust-only (NFR-017).
- The choice can be revisited without touching any caller, because the seam
  and the parity gate do not depend on the code generator.
- The Phase 4a spike records numbers; only a CG-3 blocker reopens this
  record.

## Alternatives Considered

- **LLVM.** Rejected. An LLVM binding needs a system LLVM or a bundled LLVM
  build, which breaks CG-1 item 1 for the default build, and its slower
  translation works against per-node prepare charges. Its better code quality
  is not needed for a first JIT.
- **Measure both before deciding.** Not done. The owner decided RES-56 for
  Cranelift for now; the CG-3 conditions cover the case where that proves
  wrong.
- **Use both, chosen per entry.** Rejected. Two generators double the
  boundary that FR-561 checks and the parity surface FR-563 covers, for a
  gain no measurement has shown.
