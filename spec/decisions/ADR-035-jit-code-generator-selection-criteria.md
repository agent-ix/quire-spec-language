# ADR-035: JIT code generator: decision criteria and the measurement that settles them

Status: Proposed. It stays Proposed after merge. It becomes Accepted, naming
one code generator, after the RES-56 measurement below reports. Until then
neither candidate is accepted.

## Context

ADR-029 EB-7 fixes the execution-backend seam (FR-294) and the JIT semantics
(EB-4, FR-295) and leaves the code generator to a benchmark: Cranelift or
LLVM. EB-4 binds either one. What EB-7 does not say is what the benchmark
measures and how its numbers decide. Without that, the choice can be made on
preference and justified afterwards.

The two candidates differ along lines that matter to QSL:

- **Build.** QSL's README promises that a clean clone builds with only a Rust
  toolchain (NFR-017). Cranelift is a set of crates.io crates. An LLVM
  binding needs an LLVM installation on the build host, or a bundled build of
  LLVM.
- **Translation time against code quality.** `prepare` is charged per
  translated node (FR-294 "Prepare charges"), and a JIT is only worth having
  if preparation plus execution beats the interpreter. Cranelift translates
  faster; LLVM usually produces faster code.
- **Boundaries.** Both must call only the kernel table (FR-561), report each
  generated block's byte length before it is kept (FR-294), and expose
  relocation records that FR-561-AC-3 inspects.

The coverage the JIT translates is FR-560, the fast-path rule is FR-562 and
the parity gate that holds the JIT to the interpreter is FR-563. None of them
depends on this decision.

## Decision

### CG-1 Must criteria

A candidate that fails any of these is out, whatever it measures:

1. **Rust-only default build.** The default workspace build and the
   NFR-017 clean-clone gate stay Rust-only. A candidate that needs a system
   library may exist only behind a non-default Cargo feature of `qsl-jit`,
   and it cannot be the default JIT.
2. **Prepare accounting.** The candidate lets `qsl-jit` charge
   `compile_work_units` before translating each checked node and
   `code_bytes` with each block's byte length before keeping it, and poll
   `&Cancel` at each charge (FR-294).
3. **Call boundary.** Generated code calls only `KernelTable` entries and
   blocks of the same prepared value, and the candidate exposes the
   relocation records that show it (FR-561).
4. **Determinism.** The same checked entries and `PrepareLimits` produce the
   same generated bytes before relocation, so a parity difference reproduces
   from its seed and index (FR-295, FR-563).
5. **Licence.** The candidate's licence is compatible with
   `AGPL-3.0-or-later`.
6. **Targets.** The candidate generates code for `x86_64-unknown-linux-gnu`
   and `aarch64-unknown-linux-gnu`.

### CG-2 The measurement (RES-56)

RES-56 measures each candidate that passes CG-1, with `qsl-jit` built on it,
over the FR-295 parity program generator's 10,000 units at the gate's default
seed and their argument tuples, on each CG-1 item 6 target, release profile:

| Measure | Definition |
| --- | --- |
| Prepare time | Wall time of `prepare` over every function of each unit, summed over the units |
| Run time | Wall time of every argument tuple's `call`, summed |
| Interpreter time | The same calls on the interpreter backend, summed |
| Code bytes | The `code_bytes` counter `prepare` reaches, summed |
| Build cost | Clean-clone `cargo build --locked -p qsl-jit` wall time and the number of packages it adds to `Cargo.lock` |
| Unsafe sites | The number of `unsafe` blocks and `unsafe fn` in `qsl-jit` the candidate requires |

Every measured run also passes the FR-563 parity gate. A candidate whose JIT
does not pass parity is out.

### CG-3 Decision rule

Among the candidates that pass CG-1 and parity and can be the default JIT
(CG-1 item 1), choose the one with the lower
sum of prepare time and run time on `x86_64-unknown-linux-gnu`. If the two
sums differ by less than 10 per cent, choose the one with fewer unsafe sites,
then the one with the lower build cost. If no candidate's prepare time plus
run time is below the interpreter time, accept neither: the JIT is not built
and EB-8's `jit` choice keeps refusing as not supplied (FR-296). A candidate
that needs a system library is never chosen by this rule; whether to offer
it behind a non-default feature is a separate decision after RES-56.

### CG-4 Unsafe code in `qsl-jit` (proposed)

Entering generated machine code requires `unsafe`. Every QSL crate today
declares `unsafe_code = "forbid"`. This record proposes that `qsl-jit` is the
one exception: `unsafe` confined to one module that maps generated code and
enters it, every other `qsl-jit` module and every other QSL crate keeping
`forbid`. This needs the owner's ruling before `qsl-jit` is built; the ruling
lands in this record when it is accepted.

## Consequences

- The code generator is chosen by measured numbers and a stated rule, and a
  reviewer can recompute the choice from the RES-56 report.
- A generator that needs a system library cannot become the default JIT, so
  the outside-user build (NFR-017) does not change.
- The JIT may not be built at all if it does not beat the interpreter; the
  seam and the parity gate stand either way.

## Alternatives Considered

- **Accept Cranelift now.** Rejected for this record. It is likely to pass
  CG-1, but accepting before RES-56 measures would decide on expectation.
- **Accept LLVM now for code quality.** Rejected for the same reason, and
  because CG-1 item 1 keeps it off the default build.
- **Use both, chosen per entry.** Rejected. Two generators double the
  boundary that FR-561 checks and the parity surface FR-563 covers, for a
  gain no measurement has shown.
