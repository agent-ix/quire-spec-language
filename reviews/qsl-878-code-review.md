# SR-12273: Code review (Rust lane) of QSL-878 (PR #1158)

## Summary

Ticket: QSL-878. PR quire-spec-language#1158, branch qsl-878-impl, head ea592e830. The review covers `git diff origin/main...HEAD` only: 33 files, +2936/-398. The rust-review lane is folded into this file. QSpec is cited by id only.

One focused test run went through `locked-build.sh`: `cargo test -p qsl-analyze --test it -- protocol_counted_steps bounded_closure`. It passed: 16 tests, 0 failures. It covers every new qsl-analyze test, including the adversarial lasso that replays to `Refuted` and the `WitnessFails` rejection.

The review focused on soundness: whether `check_closure` can accept a certificate for a false claim.

## Verdict

**Mergeable: no major finding.** The two medium and two low findings below are fixed in this PR, or recorded as QSL-878 remainder where the finding says so.

What is sound:

- **A closure is accepted only for a true claim.** `run_bounded` in the core checker does not trust EN-1. It re-explores every reachable product state `(model digest, BoundedState, counted distance capped at h+1)` from the real initial states with full `successors_bounded` expansion. It reads the atom itself, and rejects `BadState` on an undefined reading at a read distance, on a `Reject` monitor state, and on an `Open` terminal state that the false extension closes to `Reject`. It rejects `InitialMissing` or `SuccessorMissing` for any reached product state not in the certificate. A cut expansion still lands in `limited` or `instance_limited`, which settles `MemoryBoundReached` or `InstanceBoundReached`, never an acceptance. The case split is complete. A behaviour with infinitely many counted steps drives `remaining` to 0 and then to `Reject` for an open `eventually`. A behaviour with finitely many counted steps ends, in the finite product, inside a strongly connected set of uncounted `Open -> Open` edges. That is exactly the zero graph that `zero_progress` searches. A fair one rejects `WitnessFails`. So an accepted certificate means the clause holds on every fair behaviour.
- **Bounded key octets.** `BoundedTranslation` follows FR-338's TP-2 row and vector table: `["bounded",["origin",r],[[[],[],[[[],"positive","deadline"|"extent",r]],[]]]]`, `["accept"]`, `["reject"]`. Here `r` counts from the letter just read. `admit` refuses each negative before membership: non-canonical octets, a foreign context, an `each` clock, a clock and window that disagree, `r > h`, zero branches or more than one, a non-empty obligations, past or acceptance member, a negative polarity, and a window of the wrong kind. A `u64::MAX` horizon stays exact. `remaining == h - distance` holds for every `Open` state, so the distance in `BoundedKey` adds nothing to an open state and only separates `Accept` states up to `h+1`.
- **Fairness of the zero cycle.** Each vertex's enabled set is read from the complete expansion of its state, so a counted step a thread could take is enabled at the vertex even though it is not a zero edge. `progress_constraints` numbers every enabled and taken transition. Weak constraints need "enabled everywhere and never taken" to exclude a cycle, and strong constraints go through `analyze`'s ADR-019 refinement. Both are the #1134 kernels, not new code. So the default scheduler's per-thread weak constraint excludes the dup/lose loop while the thread at `A` is enabled, and `scheduling adversarial` does not. That is PB-3's last sentence. An unfair loop is no behaviour. Missing constraints could only make more loops fair, which means more rejections and never a wrong proof. Visibility constraints (ADR-025 MF-2) are not wired into any protocol check yet, so leaving them out here matches the rest of EN-1.
- **Termination.** The zero graph has at most the states and edges the run already charged. `analyze` charges `cancel` on every vertex and decomposition. The search cannot run without bound, though it is not charged to the budgets (FND-002).
- **Counted past windows.** `Past::step` now keeps the distances back from the last position read. On a counted step the runs shift and the previous position's lower-bound-0 truth enters at distance 1. On an uncounted step the ages and the shift stay where they are. `PastAgeCounter::step_counted` ages only on a counted step. This matches PB-3's backwards reading, and the identity `op[a,b] = op[0,b-a]` read at the last position at distance `a` holds because every distance up to `to(p)` is attained. The differential over every word of up to 4 positions covers `once`, `historically`, `since` and `triggered` with lower bounds 0 to 2, and it asserts that both verdicts occur. It is not vacuous.
- **Lasso distance in `Steps`.** `to`, `first_reaching` and `last_within` over a `Cycle` with `per_pass` (the loop's closing step included) are right. The pass arithmetic picks the least pass whose widest point reaches `need`. `per_pass == 0` returns `None` only where no position is that far (`first_reaching`) or every later position is within reach (`last_within`). Every caller maps `None` correctly: an empty future window, an unbounded `last`, the whole represented trace through the horizon, and `behind_far`'s fault, which cannot fire because `to(p) - offset <= entry` whenever `per_pass == 0`. The overflow headroom is fine: `pass * period` stays far inside `i128` for any loop that fits in memory.
- **Removed causes.** No reference to `PastIntervalInCountedSteps`, `UncountedLasso`, `UncountedLoop` or `uncounted-loop` is left in the code, specs, schemas or docs. Only the historical `reviews/qsl-561-*.md` mention them. The spine mirror (`TemporalTraceRefusal`), the wire names (`InconclusiveCause::as_str`), both settle maps and `ItemCause` are all updated together.
- **The STD-254 exception is sound and should stay.** The evaluator reads a lasso under a bounded profile only when its loop has no counted step, the closing step included. Such a loop never reaches the closed boundary or the false extension. The horizon read (`through_horizon`) still limits an `on origin` clause, and every other bounded-profile lasso is still refused (`a_lasso_under_a_bounded_profile_is_refused`). FR-338 "Protocol non-progress acceptance" already requires EN-1 to "replay it using PB-3 distances" for TP-2, which is a bounded profile. So the spec conflict is FR-329 against the more specific FR-338, and refusing would make FR-338's mandated refutation unreplayable. Only the citation is missing (FND-003).
- **Refutations are independently checked.** An EN-1 zero-progress lasso is replayed through the evaluator and the protocol replay's own fairness check (the `fairness` replay refusals), so a wrong EN-1 lasso yields a replay failure, not a wrong `refuted`. `case.label` in the adversarial test runs `replay_protocol_trace`, so "the lasso replays to Refuted" is tested, despite what the coder's note says.
- **Panic surface and errors.** The production code adds no `unwrap` or `expect`. `u64::try_from(..).unwrap_or(u64::MAX)` saturates. New errors are typed (`ZeroProgressError`, `ClosureRefusal::Fairness`), and the invariant breaks are `InternalFault`s. FR-100-AC-8 still holds: the new `Translation` re-export is a `qsl_replay` type, and no `spine` item names `qsl_eval`.
