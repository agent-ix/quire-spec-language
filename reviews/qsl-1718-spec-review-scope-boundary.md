## Summary

QSL owns translating the native admitted field order into canonical runtime record slots and executing the bytes protocol-slot path. Native selected original identities and record views remain the authority; the diff neither interprets NodeKey text to create new meaning nor adds a copied evaluator. Tests use genuine producer source and strict native reader admission before evaluation. Source replacement and the identical-value assertions exercise the intended boundary directly.

The delivered scope is canonical record order and independent evaluate/location/witness controls. Observed-slot catalog authority, complete producer object closure/handoff and atomic full identity-witness binding remain external prerequisites to full acceptance. No public supplier API, incomplete observation owner, fallback world or compatibility shim is added. The existing incomplete whole-path behavior remains explicitly outside this slice; the ticket must remain open. Projected read locations are not presented as completed-evaluation stop locations.

## Examined scope

- FR-533 (examined): For a model-owned record, the bare type environment SHALL order fields by their original selected declaration keys, the ordering the source type environment uses. Within the record's one selected document this is the byte order of `SelectedRecordFieldView::ir_identity`, not the display field name or the emitted binding position. Source-owned records keep their authored declaration order. A value constructed in either environment SHALL be usable unchanged in the other environment with the same membership, field reads and result value.
- FR-533-AC-1 (context_only): For every slot of FR-390's table that **R** holds (the activation guard, the captures of each stage, the trigger guard, the retry relation, the recovery predicate of `Partial` and `Full`, and the constraints), over the supplies of TC-1070 and TC-1315, the result and the ordered charge log over the `BarePackage` equal those over the in-process `CheckedPackage` and over the reader-backed view of an `AdmittedPackageRead`, with value, category, exit status, catalog code and cause, unavailable binder, location and losses compared, location only where the wire carries one (a read with no wire location is the unmet parity of AC-8 and is not compared). The `BareSupply` of the bare route carries the equality rows read from the handoff directory's `equality.json`, which every slot with an equality application (the integer `=` of `Refund`'s retry relation and recovery predicate included) needs.
- FR-533-AC-2 (context_only): For each outcome row of FR-520's map (true and false guard, retry relation and recovery predicate; an unavailable binder; a wrongly typed value; an unsupported construct; a meter one below measured usage), the bare route produces the successor outcome, and the exact-usage and one-below vectors of FR-390-AC-9 hold for **R**'s `retry.relation` over the `BarePackage`. The `BareSupply` of the bare route carries the equality rows read from the handoff directory's `equality.json`, which every slot with an equality application (the integer `=` of `Refund`'s retry relation and recovery predicate included) needs.
- FR-533-AC-3 (examined): A `BarePackage` whose package was read in a run in which the source unit was never compiled evaluates AC-1's slots with the results of AC-1; and over a package read from **R**'s bytes, a `BarePackage` evaluation of slot A returns the same result when the in-process `CheckedPackage` held beside it in the test is replaced by the checked package of another unit that has the same protocol node ids but a different expression at slot A, because the bare route reads no `CheckedPackage` (the in-process route's result changes with that replacement, the bare route's does not).
- FR-533-AC-7 (examined): The bare route evaluates a slot whose binder type is a record with a plain Collection member, a record with a plain Option member and a record with an Optional Collection member to the ordered charge log of the source route and to the same record value, and each binder's value type equals the source route's. Model record fields use original selected declaration-key order on both routes, including a model whose authored field order opposes its original-key order. The same value is supplied unchanged across environments; rebuilding it by display name is not parity evidence. A slot whose binder record Contract IR cannot project (its identity rows hold no field rows) refuses with `ViewFailure::Unsupported` and `MissingTypeRepresentation` at the `Node` locus of the binder, carrying `unknown_required_feature`/`unsupported-feature`, no partial value and no charge. No value of a different type is substituted.
- FR-533-AC-8 (examined): A binder unavailable and read returns `Unavailable` naming the binder and the read, with the location the package's rows give (FR-390-AC-32), equal to the in-process route's; where the wire carries no leaf location the bare result is `None` while the in-process result keeps its source location, and the test records that difference as the unmet parity of "Names and locations".
- FR-533-AC-13 (examined): Unmet parity, exact condition: two tied slots of one member (two `cases.guard` slots of a `choice`, or two ends of `related` records) have one root node (and so one walk), and their node order is the opposite of their source order (cases are held in ascending label order, so with the labels sorting against source positions the lower index is the later case in source; `related` records are held in the emitted record order). Then the bytes route gives `cases.guard[i]` the candidate origin of rank `i` and `cases.guard[j]` that of rank `j`, which are each other's source-route origins, and the two slots' `Location` values are exchanged relative to the source route; no other slot kind and no slot with a distinct root expression is affected. The value, outcome, exit status, catalog code, cause and charge log of both slots equal the source route's. No compiled unit holds two case guards with one walk (a `choice` must prove exhaustiveness, so two arms with one guard are refused at check time, and any exhaustive pair of guards differs in an application), so the rule is vectored on package copies, as FR-533-AC-14 vectors `related`. In two copies of fixture L's package edited so that `Decide.cases.guard[0]` (case `no`) and `Decide.cases.guard[1]` (case `yes`) both have the `got.ready` application as root (the guard edge of case `no` names `got.ready`; the emitted `not` application remains in the graph but its protocol-location rows under `... 2735..2748` are removed, and the rows of `got.ready` retain consecutive occurrence ordinals 0, 1, 2 over their three visits), `visible[0]`, `cases.guard[0]` and `cases.guard[1]` are three tied slots over three candidates. In the copy that keeps the labels `no` and `yes`, `cases.guard[0]` takes `... 2676..2685` (the span of the case `yes` guard, written first) and `cases.guard[1]` takes `... 2735..2748` (the span of the case `no` guard): the test asserts equal actual call values and charge logs for the two slots and these exact exchanged projected-root read `Location` values; completed evaluations have no stop location, and records the exchange as this unmet parity. In the copy whose labels are renamed, to `a` for `yes` and `b` for `no`, `cases.guard[0]` (case `a`) takes `... 2676..2685` and `cases.guard[1]` (case `b`) takes `... 2735..2748`, each its own case's span, and the test asserts that.
- FR-533-AC-14 (examined): In a copy of fixture L's package whose rows of the `decision 2641..2650` origin are removed, `Decide.visible[0]` (rank 0 of two tied slots, one candidate) takes `... 2676..2685` and view creation refuses `MissingLocationProjection` at the `Node` locus of the `got.ready` application for `Decide.cases.guard[1]` (rank 1, no candidate), carrying no partial view and no charge. In a package copy where the two ends of one `related` record of fixture L's `Got` are one application with rows under the origins `... related 99 100` and `... related 100 105`, `related.from[0]` takes `99 100` and `related.to[0]` takes `100 105` (numeric order of `(start, end)`); ordered by the UTF-8 bytes of the names `related.from[0]` would take `100 105`, so the test fails if the bytes order is used.
- FR-533-AC-17 (context_only): An inspection of the bare route finds no function that derives an equality application row, equality fact row or source-unit row from a node, a name or a source, that reads `Emission::equality_producer_identity_rows`, `equality_fact_witness_rows` or `selected_source_unit_rows`, or that selects a span-named origin by its name text other than by the rule of "Slot naming on the bytes route".
- FR-533-AC-18 (examined): The equality witness of a slot call is decided over the equality applications the slot's walk reaches, that is the applications of the slot walk (FR-383) and, at each call in it, those of the called function's body walked the same way, transitively; a function body is the one place a valid package's dependency closure and the walk differ. In a unit compiled from source in which `trigger.guard` of a copy of fixture E calls a function whose body holds an `==` application, over a supply whose equality rows are omitted, `trigger.guard` refuses `MissingEqualityWitness` at `CallAdmissionLocus::Package` with the meter untouched, and over the rows the unit's handoff writes it evaluates to the in-process route's value and charge log; a slot of the same unit that calls no function holding `==` evaluates with the rows omitted.
- TC-1333 (examined): actual call values and charge logs of the two slots equal; completed evaluations have no stop location
- FR-390-AC-66 (context_only): The in-process reader view's UnsupportedView half is not asserted here.
