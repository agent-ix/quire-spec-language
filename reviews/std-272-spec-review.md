# SR-15720: Spec review of quire-spec-language PR #1245: STD-272

## Summary

Ticket: STD-272 (unblocks QSL-976). Sub-analyses folded in: integrity, EARS, object review, failure-domain. `QSPEC_DIR=~/dev/quire-specification make check-spec-validation` exits 0 at the head; FR-121's three warnings are on unchanged lines. TC-1162 and FR-121-AC-25..27 are unique on main and across the 46 other open PR heads, and no other open PR touches FR-121. FR-400..FR-403 do not overlap this change. origin/main (43f4e2086, #1236 STD-301) is not an ancestor of the head; it touches other files and merges cleanly.

Checked and found correct: the refusal codes and causes match QSpec FR-323 and FR-342 (`invalid_model_binding`/`malformed-declaration`, `ambiguous_declaration`/`ambiguous-name`, `missing_declaration`/`missing-name`). Because `frame_operation` always names the declarer, the inherited-only refusal of FR-323 cannot arise. The process example matches FR-104-AC-10 and FR-105-AC-8 (`Flow`, `go`, `P` then `Q`, a `model`/`process` context). The state-machine example uses TC-1040's `M::OrderLifecycle::place`. The `Declined`/`InvalidInput` mapping and the `CallSiteRefusal::code` list are extended consistently. The current code resolves object types only (`model_object_tables` filters `DomainPackageRecord::ObjectType`), which matches the problem the ticket describes.

## Verdict

**NOT MERGEABLE.** The direction is right and the process half is sound. Three defects block merge. State-machine resolution contradicts FR-104, FR-081 and QSpec FR-342 on inherited operations (FND-001). The existing `UnknownOperation` rule still covers the ambiguous case that the new `AmbiguousOperation` rule refuses (FND-002). The `NotAnOperationOwner` list leaves other non-owner declarations with no refusal (FND-003). FND-004 is the FR-115 question: an inconsistency remains, and it is cheap to fix in this PR.
